## 一、tvmao 的三个静默 bug（2026-10-27 第七轮，全修）

这三个 bug 的共同特征：**都不报错**。不修就是「上游没有」的假结论。

### 1.1 行正则只认「`<a>` 独占整行」

页面 `epg-row-link` 有三种写法：

| 型 | HTML | 旧正则 |
|---|---|---|
| ① `<a>` 独占整行 | `<span class="epg-row-link"><a href="/tvcolumn/x">动画片</a></span>` | ✅ |
| ② `<a>` 夹在中间 | `<span class="epg-row-link">实况录像-2024/2025赛季<a href="/competition/y">斯诺克世界公开赛</a> 墨菲的147</span>` | ❌ 整行丢弃 |
| ③ 纯文本 | `<span class="epg-row-link">动画片</span>` | ✅ |

还有一类时间标签被漏掉：正在播出的那条 class 是 **`epg-row-playing`**（内文是「直播中」而不是时间）。

**实测代价**：`CCTV央视台球` 28 行 → 旧正则 **0 条**；抽样 24 个频道 15 个在丢数据，共丢 84 条
（CCTV-5 6→22、CCTV5+ 4→16、CCTV-7 29→38、CCTV-12 24→30、CGTN法语 25→33）。

**修法**：按 `<li class="epg-row">` 切块，块内分别取时间（`time|playing` 都吃）、取标题（剥 `<a>` 但保留前后文字）。
见 `src/sources/tvmao.mjs` 的 `parseRows()`。

### 1.2 路径猜错不报 404，而是 200 + 别人的节目单

| id | `/program/` | `/program_digital/` |
|---|---|---|
| SITV-FASHION | 200，**9行，title「DOX映画」** ✗ | 200，65行，title「生活时尚」✓ |
| SITV-CHILDREN | 200，**9行，title「DOX映画」** ✗ | 200，104行，title「动漫秀场」✓ |
| DOX-CINEMA | 200，**20行，title「CCTV-1综合」** ✗ | 200，20行 ✓ |
| KAMBA-TV | 200，**20行，title「CCTV-1综合」** ✗ | 200，48行 ✓ |
| 无连字符（114 个卫视） | 200，**20行，title「CCTV-1综合」** ✗ | 200，40行 ✓ |
| CCTVPAYFEE-* | 200 ✓ | 404 |

**这就是「生活时尚/动漫秀场补天拿到 0 条」的真因**——不是上游没有，是拿回来的是别的台。

更糟的是：代码早就抓了 `pageTitle`，注释也写着「必须校验 title」，**但实现里从来没校验过**。

**修法**：
1. 路径按前缀分组（`PATH_BY_PREFIX`），不再按「有没有连字符」一刀切
2. 强制 `titleMatchesChannel(pageTitle, expectNames)`，支持传一串名字，任一命中即通过；
   title 为空时放行（上游改版别一刀切全废掉）
3. `tvmaoPath` override 给探测也搞不定的频道钉死路径

**现行路径表**：
- `/program/` → `CCTV-` `BAMC-` `CCTVPAYFEE-` `CETV-` `CHC-` `HSCM-`（含两段式 `SHXITV/SHXITV9`）
- `/program_digital/` → `SITV-` `DOX-` `KAMBA-` `DIGITAL-`
- `/program_satellite/` → 无连字符的卫视（`AHTV1` `SANSHATV` …）

### 1.3 override 指向 catalog 外的 id 被整条丢弃

`GDTV-GDTV7`（嘉佳卡通）、`NANFANG-NANFANG6`（大湾区卫视）都不在 catalog
（catalog 只收频道清单页的链接，这两个不在清单页）。

旧代码 `log.warn` 一句就 `continue` → 该频道变「无匹配」→ 走 z51 兜底 → **永远 2 天**，
而且日志看起来是「正常跳过」。

**修法**：`tvmao`/`tvsou`/`fengshows` 允许 `override-unlisted` 直接使用
（抓不到自然留空，且有 title 校验兜底）。
⚠️ **`epgpw` 不能这样放行**——它是整包按 id 过滤，猜 id 必错。测试里有反证。

## 二、凤凰卫视（fengshows）官网 API

`鳳凰衛視香港台` 四个源（epgpw/tvsou/z51/tvmao）全无，只能走官网。

```
https://m.fengshows.com/api/v3/live/{liveId}/resources?dir=asc&date=YYYYMMDD&page=1&page_size=99
```

| 频道 | liveId | 7 天条数 |
|---|---|---|
| 中文台 | `f7f48462-9b13-485b-8101-7b54716411ec` | 296 |
| 資訊台 | `7c96b084-60e1-40a9-89c5-682b994fb680` | 382 |
| 香港台 | `15e02d92-1698-416c-af2f-3e9a872b4d78` | 294 |

**两个必须知道的坑**：

- **不带 `date` 参数会返回 2021 年的死数据**：99 条，`date` 范围 `20210709~20210710`。
  看着「有 99 条」很像正常，实际是陈年垃圾。
- **`event_time` 是 UTC**：`2026-10-26T16:00:00.000Z` = 北京 `10-27 00:00`。
  `Date.parse` 的绝对时间戳是对的，但「属于哪一天」必须按 `+08:00` 换算。

上游**不给结束时间也不给简介**（无 `end_time`/`duration`；`content`/`brief` 实测 0/49 全空），
结束时间交给 `normalize` 用下一条 start 补。

中文台/資訊台已有 7 天（epgpw），不动；只把香港台接过来。

## 三、时间轴（2026-10-27 第五轮）

### 3.1 重叠只截前一条 stop，绝不改 start

旧代码改「后一条的 start」→ 产物倒序（2 个频道）。
错的是前一条吞掉了后一条，两条都要保留，时间轴才连续，且没有编造任何时间。

### 3.2 拉短节目必须排在重叠修完之后，且只在有空位时拉

旧代码第 4 步拉长、第 5 步发现挤到下一条又截回，**两步互相抵消**，632 条一条都没修好。

### 3.3 末条 12 小时是「决定不修」

上游把末条 `stop` 写成「数据窗口末尾」，算出来 21 小时，被 `maxDurationHours = 12` 截成整齐的 12.00h。
压到 10.8h 试过，**已放弃**：那样 55 个频道在窗口末尾留 11 小时空白，
播放器显示「暂无节目」，比「一条长节目」更糟。

### 3.4 632 条 30 秒垫片是真实的

CCTV-8K/4K 的宣传片就是 30 秒，首尾相接，没有空位可以拉长。宁可显示真实 30 秒。

## 四、补天（day-fill，2026-10-27 第六轮）

### 4.1 降级链「有 1 条就 break」让 44 个频道只 1~2 天

epg.pw 的 CN 包对 352 个频道只给滚动 24h（`16h 8h 0 0 0 0 0`），
拿到 1 条就停，轮不到 tvmao 的 7 天。

**修法是「合并非换源」**：epg.pw 有简介，tvmao 有 7 天，换源等于拆东墙补西墙。

### 4.2 ★ 重叠记录会被 normalize 删掉带简介的主源

`normalize` 第 5 步 `if (cur.startTs < prev.stopTs) prev.stopTs = cur.startTs` 然后 filter 掉零长度。
同 start 不同 title 时，**前一条（带简介的主源）被截成零长度→删除**，留下的是无简介的那条。

所以补天必须**逐条判重叠、整条丢弃、不裁剪**（`pickMissingDays`）。
测试 `test/day-fill.test.mjs` 的 `[16]` 是反证。

### 4.3 ★ 区域版本必须校验（2026-10-28 收紧，别改回去）

`nameVariants('CCTV4欧洲')` → `['cctv4欧洲','cctv4']`，裸 `cctv4` 与
`nameVariants('CCTV-4 (亚洲)')` → `['cctv4']` 撞车，
把国内版电视剧《爱在青山绿水间》补进了欧洲版。

`sameRegionVersion` 现行规则（三层）：
1. 两边都有区域词 → 必须重合，否则拒
2. 一边有一边没有，且**有词那侧是「具体分版」**（欧洲/美洲/海外/境外/北美/南美/西欧/东欧）→ **拒**
3. 一边有一边没有，有词那侧是「默认区域」（亚洲/香港/台湾/大陆/内地）→ 放行

★ 为什么规则 2 必须存在（2026-10-28 事故）：
   旧规则是「一边没有区域词 = 默认版，一律放行」。但**裸 `CCTV-4` 恰恰就是亚洲版**，
   不是"通用版"。本地一次 epgpw 抽风，CCTV4欧洲(539832) / CCTV4美洲(539751) 抓空，
   降级链降到 `webncode:nowtv_542(CCTV-4)` = 亚洲版 → 三台全播国内版节目。
   报表显示「278 条 7 天」，**比原来源还完整，日志零异常**。
   → 这类错误比"节目少"危险得多：数据看着更好，内容是错的。

★ 规则 2 也**必须**加在降级链上，不只是补天分支：
   第六轮只给「补天」加了校验，降级链漏了，于是主源一抓空就串台。
   两个方向都会串：`CCTV4欧洲 → CCTV-4(亚洲)`、`CCTV4亚洲 → CCTV-4(美洲)`。
   实现在 `index.mjs` 的 chain filter 里，主源（idx 0）永远保留。

⚠️ 「欧」= 「欧洲」要用 `REGION_ALIAS` 归一，且用 lookbehind 避免「欧洲」被「欧」先吃掉。
⚠️ 「国际」**不能**放进 `SPECIFIC_REGION`：tvmao 把亚洲版叫「CCTV-4国际」，
   放进去会误拒一批正确配对（实测「湖南卫视」vs「湖南卫视国际」也靠另一道防线拦）。
⚠️ 回归用例在 `test/day-fill.test.mjs` 的 `mustRejectNoRegion`，共 5 条，别删。

### 4.4 「天数够不够」按覆盖小时，不按条数

求索纪录一天 12 条但覆盖满 24h（每条 2 小时）；电影台一天 10 条、新闻台一天 40 条，条数差 4 倍。
判据：`medHours >= 8 && v.hours < medHours * 0.5`，且要排除窗口最后一天。

## 五、简介（desc）

### 5.1 ★ desc 复读标题会锁死补简介位置

三源循环都 `if (isRealDesc) continue`，复读的 desc 骗过判断 → 真简介补不进。

`isEchoDesc`：`desc === title`，或 `desc = title + 尾巴`（剥数字/EP/季/集后 ≤2 字）。
⚠️ **别放宽成「以标题开头」**，会误伤 1177 条。

### 5.2 ★ 实体解码必须循环解到稳定

源里存 `&amp;quot;`，旧实现顺序错 → 产物留字面乱码 405 条（用户看到 `&quot;融媒体&quot;`）。

### 5.3 统计别只看非空或长度

统一走 `utils.hasRealDesc` = `isRealDesc`（≥12 字 + 非占位）+ `!isEchoDesc`。

### 5.4 简介索引必须按频道分开

三级：`buildChannelIndex` → `alignByTitles` → `buildGlobalIndex`（只收全站唯一）。
⚠️ 归一化必须繁简转换。

## 六、频道对齐

### 6.1 不能用名字匹配

`台視新聞` → `台視` 必串台。用「节目标题交集」（≥5 条且 ≥15%）。

### 6.2 非中文标题只能人工映射

港台35 转 CGTN 英文、延边朝鲜语，写 `overrides.json` 的 `titleMap`。
⚠️ **别用「起始时间相同」对齐**。

### 6.3 「上游没有」不能靠名字匹配下结论

`AsianFood` ↔ `亞洲美食頻道` 字面差得远但数据在。
要把上游有节目的频道人工扫一遍。

### 6.4 「清单页没有」≠「站点没有」

`GDTV-GDTV7` / `NANFANG-NANFANG6` / `SHXITV/SHXITV9` 都不在 catalog，但数据在。

### 6.5 epg.pw 的 display-name 会撒谎

`My Cinema Europe` 实为半岛英文台、`CGTN西语` 实为中文节目。

### 6.6 同名跨版本不可信

z51 的「CCTV4」是国内版（放电视剧），与 CCTV4欧洲/美洲交集仅 50~57%，合并前必须验证。

### 6.7 ★★ 源自报的 days/count 会骗排序（2026-10-28 新增，别改回去）

`pickBest` 按「天数 → 简介数 → 条数」选源，前两个维度**全靠源自己报**。
新源如果为了"显得数据全"而硬编码 `days: 7`、`count: 0`，就会稳定赢过数据更好的老源，
而且**构建产物看起来完全正常**。

实测事故（接 webncode 第一版）：
| 频道 | epgpw（真实） | webncode（自报 days=7） | 结果 |
|---|---|---|---|
| Now新聞台 | 6天 325条 **323简介** | 5天 273条 133简介 | 简介 323→133 |
| Now財經台 | 6天 291条 **286简介** | 5天 306条 136简介 | 简介 286→136 |

两个台简介掉一半以上，日志只有一行「匹配成功」。

三条硬规则：
1. **`days` 必须真探**，不能给常数。webncode 读 `availableDates.length`（246 台 ×1 请求，6 并发 ~30s，
   结果进 `catalog.json` 缓存 24h，日常 build 复用）。
2. **`count` 必须真数**，不能恒 0。litv 包已在内存里，零成本精确统计；
   webncode 用「当天条数 × 天数」外推，口径对齐 epgpw 的全期总条数。
3. **`pickBest` 必须有简介维度**（`withDesc`）。只有天数和条数时，
   「条数多但简介全空」的源会稳定赢——而简介恰恰是本项目最稀缺的资源（整体 60%）。
   排序：`days → withDesc → count → 名字长度`，`rankAlternatives` 同序。

⚠️ `withDesc` 缺失时按 0 处理 = 退回旧行为，不会误伤（旧 catalog 缓存靠 TTL 自愈）。
⚠️ 统计一律走 `utils.hasRealDesc(desc, title)`，别只判非空（§5.3）。
⚠️ 新接源时先跑一次 `catalog` 看重扫后的 `days/withDesc` 分布，
   再用 `node src/index.mjs build` 对比 `output/report.json` 里这些台的 `count/withDesc` 前后差异。

#### 6.7b ★★ 「单日条数 × 天数」外推也是自报（2026-10-28 第九轮，TDM 二次中招）

修完 webncode 后我以为「真探一天 + 外推」够安全了，接 TDM 时又这么写：
```js
const r = await getDayProgrammes(cid, 1, today)   // 只探今天
days = MAX_DAYS                                    // 常数 8
count = r.programmes.length * MAX_DAYS             // 外推
withDesc = 真简介数 * MAX_DAYS
```
CI 实测对比（同一次 run）：

| 台 | 自报 | 实测 | 虚高 |
|---|---|---|---|
| 澳視澳門 | 8天 **376条** | 6天 **272条** | +38% |
| 澳門資訊 | 8天 **392条** | 6天 **303条** | +29% |
| 澳門-Macau | 8天 **360条** | 6天 **293条** | +23% |
| 澳視葡文 | 8天 144条 | 6天 107条 | +35% |
| 澳門體育 | 8天 120条 | 6天 107条 | +12% |
| 澳門綜藝 | 8天 128条 | 6天 95条 | +35% |
| **合计** | **1520条** | **1177条** | **+29%** |

**根因不是「外推算术错」，是「窗口跟着今天滚动」**：
我手工探测那刻是 10-28，窗口是 `10-26 ~ 11-02`（今天-2 ~ 今天+5）；
CI 跑的时候从**今天**往后探 8 天 → `10-28 ~ 11-04`，而后 2 天（11-03/11-04）是空的，
实际只拿到 6 天。**同样的代码，换个日期跑，天数就变了。**

硬规则（补充到 §6.7 三条之后）：
4. **天数不能靠「窗口大小」推断，只能数「探到几个非空日期」。**
   凡是「滚动窗口型」源（TDM 这种 `今天-N ~ 今天+M`），`days` 唯一正确算法是
   `new Set(探到的非空 ymd).size`，`count/withDesc` 同轮累加，不许乘。
5. **手工探测的日期 ≠ CI 跑的日期时，天数结论不可信。**
   我 10-28 手工看到 8 天、CI 也是 10-28 但只探到 6 天——差别在「从哪天起探」。
   写 `listChannels` 时要按**窗口语义**（±N 天）枚举日期，而不是「从今天起 N 天」。
6. **代价换准确**：TDM 逐日真探 = 6 台 × 8 日期 = 48 个请求（简介靠 `_descCache`
   跨天复用，实际增量远小于 48×40）。这点请求量换 29% 的数字准确，划算。
   别为了省请求退回外推——外推错的是**排序输入**，错了不报错。

#### 6.7c ★★ 「真探」之后还有口径坑：过去的天不能数进 `days`（2026-10-28 第九轮）

改成逐日真探后，TDM 报出 **9 天**（10-25 ~ 11-02），比 epgpw 的 7 天还多，
于是在 `pickBest` 里以「天数最多」稳赢——但那 3 天是**已经过去**的。

**根因**：TDM 的窗口含过去 2~3 天（`今天-2 ~ 今天+5`），我把 -3 ~ +6 全探了并全数进 `days`。
而 build 只从**今天**起覆盖 7 天，过去的天一条也用不上。数字「真」但**口径错**，
比自报虚高更危险——因为它看起来是真的。

各源 `days` 实际口径（2026-10-28 catalog 实测分布）：

| 源 | days 最大值 | 说明 |
|---|---|---|
| epgpw | 8 | 上游 XMLTV 含今天及以后 |
| webncode | 9 | `availableDates.length`（含今天） |
| litv | 6 | 包里所有 Schedule 日期 |
| tdm（修正前） | **9** | ← 含过去 3 天，虚 |
| tdm（修正后） | **6** | 只计今天及以后 |

硬规则：
7. **`days` 的语义固定为「今天及以后有几天的数据」**，与 epgpw / build 覆盖窗口对齐。
   加新源时先问：这个源的窗口含不含过去？含的话必须切掉再计数。
   切法：`if (ymd >= todayYmd)`，`todayYmd` 用北京时间 `new Date(Date.now()+8*3600e3)`。
8. **过去的天探还是要探**（别为省请求删掉），只是不计入 `days/count/withDesc`。
   理由：上游有时把今天的数据挂在昨天 key 上，探一下能发现；但计数必须干净。
9. **口径不一致比数字虚高更隐蔽**：虚高会被「自报 vs 实测」对比抓出来，
   口径错的两边都是真数，任何审计都发现不了，只有在 `pickBest` 排序结果里才显形。
   → 验证方法：`catalog.json` 里按源统计 `days` 分布，**任何源的最大值明显大于其他源就要查口径**。

### 6.8 ★★ 罗马数字 Ⅰ~Ⅻ 必须先转阿拉伯数字（2026-10-28 新增）

`normalizeName` 末尾的白名单 `s.replace(/[^a-z0-9+\u4e00-\u9fa5]/g, '')`
把 `Ⅰ`(U+2160)~`Ⅻ` 当噪声**直接删掉**，于是：

| 目标频道 | 归一化后 | 结果 |
|---|---|---|
| 好消息Ⅰ | `好消息` | ↓ 两者相同 |
| 好消息Ⅱ | `好消息` | ↑ 指向同一 sourceId |

**后一个台拿到前一个台的节目，完全静默**——两个台都在产物里，都"有节目"，
只是内容错了。这类错误在报表上表现为「两个台数据一模一样」。

实测中招 **4 组 8 个台**：好消息Ⅰ/Ⅱ、大爱Ⅰ/Ⅱ、博斯运动Ⅰ/Ⅱ、博斯高球Ⅰ/Ⅱ。

修复：在 `s.toLowerCase()` **之前**插入转换（必须在前，否则已被删掉）：
```js
s = s.replace(/[ⅠⅡⅢⅣⅤⅥⅦⅧⅨⅩⅪⅫ]/g, (c) => String('ⅠⅡⅢⅣⅤⅥⅦⅧⅨⅩⅪⅫ'.indexOf(c) + 1))
s = s.replace(/[ⅰⅱⅲⅳⅴⅵⅶⅷⅸⅹ]/g, (c) => String('ⅰⅱⅲⅳⅴⅵⅶⅷⅸⅹ'.indexOf(c) + 1))
```
修后 `博斯高球Ⅰ` → `博斯高球1`、`博斯高球Ⅱ` → `博斯高球2`，重复映射 4 处 → **0**。

⚠️ 修完仍要注意：`博斯高球Ⅱ` → `博斯高球2`，而 litv 侧叫「博斯高球二台」→ `博斯高球二`，
**两者仍不相等**，Ⅱ 还得靠 aliases 或 override 才能对上。
⚠️ 同类隐患：任何「看起来像噪声、实际带语义」的字符都可能被白名单吃掉。
   现在注释里已标明「三个必须保留的语义字符」，加新源时留意。
⚠️ 验证方法：`git show origin/output:report.json` 后扫 detail，
   **两个目标频道 usedSource 完全相同 = 疑似归一化撞车**，不是"正常复用"。

## 七、工程 / 环境

### 7.1 上游改版是静默的

tvmao 换路径后全消失，日志只报「跳过」。
★ **`catalog.json` TTL 24h，加新源后必须 `catalog` 重扫**，否则 match 报「源清单中不存在」。

### 7.1b ★★ epg.pw 的「1 天台」是滚动 24 小时窗口，**凌晨跑会集体变空**

epg.pw 有 **443 / 1360 = 33%** 的台只给「滚动 24 小时」（`days=1`，约 20~30 条）。
这 443 个台**不是数据缺失，是窗口形态**——它只给「现在往前 24 小时」。

实测（2026-10-27 同一天两轮 CI，上游包大小完全一致）：

| 跑的时刻 | epgpw 主源 | 空频道 | 节目总数 | z51 兜底 |
|---|---|---|---|---|
| 北京 22:16（UTC 14:16） | **248** | 8 | 55693 | 少量 |
| 北京 01:04（UTC 17:04） | **185** | 29 | 52685 | **18 个，只剩 1~2 天** |

同一份 `catalog.json`、同一份代码、同样的包大小（CN 8.2MB / HK 14.8MB / TW 22.7MB），
差别只在**跑的时刻**。凌晨刚过零点，地方台还没发布新一天节目，滚动窗口里是空的。

→ 判断"某次产物变差是不是回归"时，**先看 UTC 时刻**，别急着改代码。
   验证方法：对比 `.cache/epgpw_CN.xml` 大小，大小一致就说明上游没变、是时段问题。
→ 这也是「数字只能取 CI 产物」之外的第二条口径要求：**要注明跑的时刻**，
   22:16 和 01:04 的产物不可直接比较。

⚠️ 注意 `catalog.json` 里 `days=1` 的台，其 `count` 是**探测那一刻**的窗口内容，
   不代表运行时还有数据。所以 catalog 的 days/count 只能用于「选源排序」，
   不能当作「这个台一定有节目」的承诺。

### 7.2 行尾

`channels.json` / `index.mjs` / `README.md` 是 CRLF，其余 LF。
⚠️ `grep -c $'\r$'` 在 Git Bash 误报，**用 Node 核对**。
Python `io.open(p,'w')` 会转 CRLF，必须 `newline='\n'`。

### 7.4 其他环境坑

- **改 workflow 走 `gh api`**（remote token 只有 repo scope）
- **Pages 需先有 gh-pages 否则 422**
- **jsdelivr UA 反爬是反的**（浏览器 UA 403），`m3u <URL>` 用 curl UA
- **epg.pw 的 `+0000` 是假的**（按 `+0800`）
- **同 region 并发写坏缓存**，已用 inflight 去重
- `check` 会重写 `catalog.json` 产生噪音 diff，提交前 `git checkout --` 掉
- **`z51` 不在 catalog**，写 `z51SourceId`，只对「节目为 0」的频道生效

### 7.5 审计脚本也会骗人

② 「含 `&lt;`」是假阳性
③ `epg-m3u.xml` 的 id 已改写，不能对 `channels.json` 判地区
④ 「某天条数少」要排除窗口最后一天

### 7.6 文档数字必须写清分子分母

`count` 是节目总数、`withDesc` 才是简介数。
