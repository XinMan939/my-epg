# 把节目单挂到自己的直播源上（M3U 对接）

> 本文回答一个具体问题：**我自己抓的 m3u 直播源，能不能用这份 EPG？**
> 结论：能。但两边的频道 id 体系不同，直接订阅一个台都挂不上，必须生成一份 id 改写版。
> 全部数字都是对 [XinMan939/iptv-api](https://github.com/XinMan939/iptv-api) 的 `output/result.m3u` 实测得出的。

## 一、为什么直接用 epg.xml 挂不上

| | 我们（epg.xml） | 你的 m3u（result.m3u） |
|---|---|---|
| channel id 写法 | `CCTV1.cn` `ZhejiangSatelliteTV.cn` `Jade.hk`（iptv-org 规范） | `CCTV1` `浙江卫视` `TVB翡翠`（裸名） |
| 名字写法 | `CCTV-1 综合` | `CCTV1` / `CCTV-1` / `CCTV-1 HD` 混排 |

播放器挂节目单靠 `tvg-id` 与 `<channel id>` **字符串相等**。两边一个都不相等 → 直接订阅等于没挂。这不是内容问题，是 id 体系问题。

## 二、解法：两条命令

```bash
# 1) 对齐：m3u 的地址（本地路径或 URL 都行）
node src/index.mjs m3u https://raw.githubusercontent.com/XinMan939/iptv-api/master/output/result.m3u

# 2) 构建：会额外产出 output/epg-m3u.xml / .gz
node src/index.mjs build
```

- `channels/m3u-map.json` —— 映射表（**建议入库**，CI 直接复用，不用每次都跑第 1 步）
- `output/epg-m3u.xml` —— 对接版，`<channel id>` 已经是你的 `tvg-id`

```xml
<channel id="CCTV1">                      <!-- 不是 CCTV1.cn -->
  <display-name lang="zh">CCTV-1 综合</display-name>
  <display-name lang="zh">CCTV1</display-name>   <!-- 补上你那边原本的写法 -->
```

播放器里 **EPG 填 `epg-m3u.xml.gz`、直播源填你的 m3u**，两边都不用改。

## 三、匹配规则：五级，宁可漏不可串台

| 级别 | 规则 | 命中 |
|---|---|---|
| ① manual | `m3u-map.json` 里手工写死的映射，优先级最高 | 0 |
| ② id-exact | 两边 id 完全相等（扩容后大量命中——新频道的 id 就是按 tvg-id 起的） | 0 |
| ③ id-stripped | 我们的 id 去掉 `.cn/.hk/.tw/.mo` 后相等 | 109 |
| ④ name-unique | 名字/别名归一化后相等，且该名字在我方与 m3u 两侧都唯一 | 142 |
| ⑤ name-loose | 再去掉台标前缀（TVB/CCTV）和「卫视/电视/频道/台」，两侧仍唯一 | 5 |

**为什么必须两侧都唯一**：宽松规则会塌名字（湖南卫视 / 湖南国际 都塌成「湖南」）。只要某一侧塌出歧义就直接放弃，绝不猜。

### 归一化这一步是真正的脏活

一开始 318 个 tvg-id 里只对得上 90 个，剩下的大半不是「没有这个台」，而是名字没归一干净。逐条修出来的规则：

| 坑 | 表现 | 处理 |
|---|---|---|
| 繁简不统一 | `鳳凰衛視香港台` vs `凤凰香港`、`三立台灣台` vs `三立台湾` | 接入 OpenCC 完整字表（3221 字），不再靠手写表补字 |
| 手写繁简表漏字 | 漏一个「緯」→`緯來育樂台` 永远对不上 `纬来育乐`，整类台湾频道假性缺口 | 同上，`src/t2s.mjs` 兜底 |
| 台标前缀 | `TVB翡翠` vs `翡翠台`、`CCTV兵器科技` vs `兵器科技` | 剥前缀，但要求剩下部分**以汉字开头**，否则 `TVBS欢乐` 会变成 `s欢乐` |
| 结尾「台/频道」 | `無綫新聞台` vs `TVB无线新闻` | 去尾部「台」，去「卫视/电视/频道」 |
| 圈码 / 罗马数字 | `大爱Ⅰ` `大爱Ⅱ` 都塌成「大爱」→ 撞车被判不可匹配 | ①Ⅰ②Ⅱ 等统一成阿拉伯数字 |
| 画质后缀误伤 | `CCTV-4K` 被剥成 `cctv`，和 `CCTV-8K` 撞车 | 后缀只剥结尾、且**不剥 4k/8k**（它们是频道本身的区别） |

### 新频道的 id 怎么定的

1. **优先用 iptv-org 官方 id**（拿 `iptv-org/api/channels.json` 按名字对，83 个对上了，如 `CCTVWeaponTechnology.cn` `VideolandDrama.tw` `EBCMovie.tw`）
2. **对不上的用 `<你的tvg-id>.<国家码>`**（78 个，如 `纬来育乐.cn`、`靖天电影.tw`）

第 2 种是刻意这么定的：这些台 iptv-org 根本没有条目（台湾的靖天、龙华、博斯系列，大陆的求索、睛彩系列），与其编一个假英文名，不如直接沿用你 m3u 里的写法 —— 这样它天然是 `id-exact` 命中，也不存在以后名字漂移的风险。

## 七、必须记住的几个坑

**时间轴对齐不可靠。** 试过按节目开始时间对齐（延边卫视朝鲜语标题 → 51zmt 中文标题），TOL=15 分钟能对出 12 组，但 `일기예보`（天气预报）被错配成「看神州」—— 两边时间轴本身有错位。已放弃，改走人工 `titleMap`（`channels/overrides.json`）。

**不要用「包含匹配」兜底。** 剩下的 55 个缺口里有 `澳视体育`/`澳视资讯`、`睛彩篮球`/`睛彩竞技`，包含匹配很容易把 `CCTV5+` 吸到 `CCTV5`、`台視新聞` 吸到 `台視`。宁可空着。

**★ 缺口结论不能只靠名字匹配得出。** 上一版把 7 个台判成「上游没有」，全错 —— `AsianFood` 在 epg.pw 叫 `亞洲美食頻道`，`阿里郎` 叫 `韓國阿里郎`，`农林卫视` 叫 `陕西农林卫视`。名字差得远，任何自动匹配都不可能命中，但数据一直都在。判断「上游有没有」的正确口径是**把上游有节目的频道全列出来人工扫一遍**，不是跑一次名字匹配就下结论。

**★ display-name 会撒谎。** epg.pw 的 `370247` 名字是「My Cinema Europe HD 我的歐洲電影」，节目却是半岛英文台；`570483` 名字是「CGTN西语」，节目却是中文。收录前必须抽几条节目名看内容，只核名字会挂错台。

**★ 上游站点改版是静默的，日志只报「跳过」。** 2026-10-27 tvmao 改版，频道列表页的链接从
`/program/cctv/CCTV1-w1.html` 变成 `/program/CCTV-CCTV1-w2.html`，卫视从 `/program/` 变成 `/program_satellite/`。
旧正则一条都匹配不上 → tvmao 源 **214 个频道全部消失**，日志只有一句
`[WARN] 源清单里没有 tvmao 频道，跳过`，不报错、不失败。
后果：简介率从 61.2% 掉到 60%，央视有节目的从 41 个掉到 38 个 —— **看起来像「上游数据变差了」，其实是源整个没了。**

更隐蔽的是 `catalog.json` 缓存 24 小时：正则修好后再跑 build，仍在复用**坏掉时生成的缓存**，问题依旧。
修完必须 `node src/index.mjs catalog` 强制重扫。修复后：频道 255→263、节目 41268→44796、简介 60%→62.3%。

> 排查口诀：**看到「源清单里没有 XXX 频道」这种 warning，不要当成正常跳过，先去看那个源的 listChannels 是不是挂了。**

**★ 时间窗口会吃掉「只有昨天」的频道。** epg.pw 的 CN 包长期有 352 个频道只给昨天一天数据（今天还没更新）。
构建窗口从今天 0 点起，这些频道的节目全部被过滤 → 表现成「匹配上了但 0 条节目」。
`农林卫视`(570491) / `汕头经济`(544379) 现在就是这状态：匹配正确、源里有数据，但要等 epg.pw 更新当天才会出现。
判断方法：直接看源包里该 id 的 `start` 日期分布，别只看条数。

## 九、2026-10-27 第三轮：3 个新源 + 2 个隐藏故障

用户给了 5 个链接，实测后结论是 **3 个真源、1 个无简介、1 个打脸 tvmao 路径**。

### 9.1 kbro（台湾大宽频）—— 港台简介主力

`twmbroadband.com` 的页面是 JS 空壳，真接口在 `js/v2/program.js` 里：

```
GET https://epg.kbro.com.tw:2543/epg/epg_channel.php?appid=WEB
GET https://epg.kbro.com.tw:2543/epg/epg_program.php?appid=TFM&date=YYYYMMDD
```

- **日期是 `YYYYMMDD`**，传 `2026-10-27` 返回 0 字节
- **只给 3 天**（今天 +2），所以定位是**简介源**不是节目单源
- 296 频道 / 251 有节目 / 213 带真简介，大量 100%

**净贡献：982 条简介**（CI 2026-10-27 实测：频道级 622 + 全局级 360；剔除频道宣传语 348 条、挡掉跨区套用 27 条后）。最大单台是公視 1% → 56%。

#### ★ 两个必须记住的做法

**① 简介索引绝不能做「全局一张表」。**
第一版建 `Map<标题, 简介>`，结果「午間新聞」被套上「鏡電視新聞台」的宣传语，
所有台的午间新闻变成同一句，只补到 175 条。必须按 z51 那套两级来：

1. `buildChannelIndex` → `Map<channelId, {titles:Set, descMap:Map}>`
2. `alignByTitles` → 标题交集对齐频道（≥5 条且 ≥15%）
3. `buildGlobalIndex` → 兜底，**只收「全站唯一」或「全站 desc 一致」的标题**

**② 频道对齐有两条通道，缺一条会漏一批真数据。**

| 通道 | 条件 | 作用 |
|---|---|---|
| ① 标题交集 | ≥5 条且 ≥15% | 内容级证据，最可信 |
| ② 名字完全相等 | 归一化后**完全相等**，且交集 ≥2 | 补 ① 漏掉的 |

kbro 只给 3 天、我方是 7 天，两边节目单天然只重叠一部分，交集偏小 →
纬来精采（inter=4 rate=13%）、Catchplay（6/11%）、博斯网球（2/6%）都被 ① 误杀，
但它们的名字和 kbro 完全一样。加 ② 后对齐 66 → 75 个频道，补的条数 873 → 889
（CI 2026-10-27 实测：对齐 75 个 / 284 个目标，补 982 条 = 频道级 622 + 全局级 360）。

⚠️ ② **只能「完全相等」，绝不能「包含」**。港台名字天生互相包含：
`台視` ⊂ `台視新聞`、`博斯網球台` vs `博斯運動台`、`中天綜合台` vs `中天新聞`。
弱匹配里的反面例子（翡翠台被算到鏡電視新聞台、GoodTVⅠ 被算到好消息HD）全是靠 ② 挡掉的。

⚠️ 归一化要剥**结尾**的「電視台/电视台/頻道/频道/台」，但只剥结尾：
`台視` 的「台」在开头，全局替换会变成「視」。靠这条救回纬来精采、靖天映画、DW德国之声。

### 9.2 tvmao：两段式路径 + 两个解析故障

用户给的 `tvmao.com/program/SHXITV/SHXITV9`（农林卫视）是两段式路径，
我们的 `listChannels` 正则只收 `[A-Za-z0-9\-]+`，永远匹配不到 → 之前判成「tvmao 没有农林卫视」。

**「清单页没有」不等于「站点没有」。**

顺着这条线挖出两个故障，**都不是上游的问题**：

**故障 A：`inferPath` 的数字付费规则失效。**
旧规则「`CCTVPAYFEE-` 走 `/program_digital/`」现在 404：

```
/program/CCTVPAYFEE-CCTVPAYFEE35-w2.html   200 68862B  ✓ CCTV中学生频道
/program_digital/CCTVPAYFEE-...-w2.html    404    92B  ✗
/program/BAMC-CWJINGDIAN-w2.html           200 58942B  ✓ 重温经典频道
```

`BAMC-` 前缀不在任何规则里 → 归到 satellite 分支 → 404 → 又以为「上游没有」。
**新规则：sourceId 含连字符（`XXX-YYY` 二级分组）一律走 `/program/`。**

**故障 B：节目行有两种结构，解析器只认一种。**

```html
A) <span class="epg-row-link"><a href="/tvcolumn/xxx">节目名</a>尾巴</span>   ← 收录成词条
B) <span class="epg-row-link">动画片</span>                                ← 没收录词条
```

旧正则只认 A：
- 重温经典频道 22 条**全是 B** → 一条抓不到，表现成「这个频道没节目」
- 农林卫视 17 条 A + 34 条 B → 只抓到 17 条，**丢了三分之二**

修完：CCTV中学生 19→34、重温经典 0→**21**、农林卫视 17→**40**。

### 9.4 ★ 上线后复查揪出的串台事故（比缺简介严重得多）

kbro 接入后 CI 跑绿、覆盖率涨了，但**抽查线上产物**发现简介挂错了台：

| 频道 | 节目 | 被灌进去的简介 | 真实情况 |
|---|---|---|---|
| CCTV-1 | 晚间新闻 | 「鏡電視新聞台，帶領台灣觀眾開啟不一樣的新聞視野…」 | CCTV-1 自己的品牌栏目 |
| 江苏卫视 | 非诚勿扰 | 「留学海外的秦奋回到北京探望母亲…」（冯小刚电影剧情） | 相亲综艺栏目 |
| 广东民生 | 健康之道 | 「健康之道 綜藝-多元座談-台語」 | 广东本地健康节目 |
| 香港多个台 | 晚間新聞 | 同上鏡電視宣传语 | 各台自己的新闻 |

**根因：`全站唯一` 不等于 `是同一个节目`。**

全局兜底的设计是「某个标题在源里只出现一次 → 无可争议」。但对**跨地区**的通用栏目名，
这条规则完全失效：kbro 296 个频道全是台湾台，「晚間新聞」恰好只有鏡電視新聞台给了简介，
它就成了「唯一答案」，被当成通用答案灌到所有地区的「晚間新聞」上。

**两层修复：**

**① kbro 全局兜底加地区限制**（`regionOf(t) === 'TW'` 才允许走全局索引）
kbro 全是台湾台，跨区套用没有依据。挡掉 27 条。
频道级对齐不受影响（那是同一个台，跨区也对，如 `HBO电影.tw ↔ HBO HD頻道`）。

**② 剔除 kbro 频道内的「频道宣传语」**
台湾有些台把频道介绍填进了每个节目的 `programdescr`：

| 频道 | 节目数 | 唯一 desc 数 | 内容 |
|---|---|---|---|
| 彩虹頻道HD | 41 | 1 | 「彩虹成人數位頻道將家庭的成人娛樂享受高規格化…」 |
| 彩虹電影台HD | 30 | 1 | 「彩虹電影台，全天不間斷放送限制級電影…」 |
| 鏡電視新聞台HD | 13 | 1 | 「鏡電視新聞台，帶領台灣觀眾開啟不一樣的新聞視野…」 |
| 民視新聞台HD | 16 | 1 | 「民視新聞堅持內容公正、報導深入…」 |

判据：**本台 ≥3 个不同标题复用同一句 desc** → 是宣传语。
实测命中 40 组、剔除 348 条，**全部是宣传语，零误伤**。
（对比：按「跨台重复」判会误伤 —— 「台視新聞部製作的專題深入報導」在 2 个台都有，那是同集团共用稿。）

**③ 51zmt 侧只做显式黑名单，不做自动判据**

「非诚勿扰」在 51zmt 里同名条目只出现在「CatchPlay电影」一次。试过三轮自动判据：

| 判据 | 挡掉 | 误伤 |
|---|---|---|
| 按地区（港台来源 → 大陆目标） | 8 | **800**（卫视播同部电视剧是对的，如港台31「追風者」） |
| 按新闻类型（新闻/时事/财经禁跨台） | 818 | **818 全误伤**（「新闻联播」各台统一转播，简介相同是对的） |
| 来源是电影台 + 目标非电影台 | 34 | **34**（HBO温馨家庭播电影是对的、Catchplay自己播也是对的） |

真错只有 7 条，误伤是真错的 4~100 倍。所以只留 `overrides.json` 的 `blockTitles`：

```json
"JiangsuSatelliteTV.cn": { "blockTitles": ["非诚勿扰"] }
```

命中就跳过全局兜底 → 江苏卫视的「非诚勿扰」现在**留空**。宁空不挂错。

**代价与收益：**

| | 修复前（CI 40450630305） | 串台修复（CI 40456761792） | 口径修正（CI 40461166344） |
|---|---|---|---|
| 真实简介 | 29190 / 46974 = **62.1%** | 29116 / 46973 = **62.0%** | 28441 / 46973 = **60.5%** |
| kbro 补的条数 | 1017 条（含串台） | 950 条（干净） | 982 条（干净） |
| 串台 | 跨区 123 条 + 宣传语 348 条 | **0** | **0** |
| desc 复读标题 | 799 条被当成真简介 | 799 条被当成真简介 | **0**（640 条排除 + 部分被真简介覆盖） |
| desc 双重转义乱码 | 405 条 | 405 条 | **0** |

**用 1.5 个百分点换零串台、零废话、零乱码，值得。**
最后这 1.5 个百分点不是数据变少了，是**口径修正** —— 原来那 62.0% 里有 799 条「desc 就是把标题抄一遍」
的废话被算成了真简介。真实简介的绝对条数其实只从 29116 降到 28441（-675），
因为其中 261 条在这轮被后续源补上了真简介。

用户点开「CCTV-1 晚间新闻」看到台湾新闻台的宣传语，或者看到 `&quot;融媒体&quot;` 这种乱码，
比看不到简介糟糕得多。

| `重温经典.cn` | tvmao `BAMC-CWJINGDIAN` | 21 条 |
| `农林卫视.cn` | epgpw `570491` → 降级 tvmao `SHXITV/SHXITV9` | 40 条 |

**空频道从 19 个降到 9 个。**

## 十、2026-10-27 第四轮：两类「看着有简介、实际是废话」的数据

这一轮不是接新源，是**复查产物时发现两个一直存在的缺陷**。它们都不会报错、CI 全绿，
但用户点开节目看到的东西是错的。

### 10.1 ★ desc 就是标题抄一遍 —— 799 条，而且会锁死补简介

epg.pw 台湾包有一批节目的 `<desc>` 与 `<title>` 一字不差：

```
博斯無限台    「2025-26 司諾克賽季 世界大獎賽 四強(1)ZHA vs WAK」
             → desc 完全相同
博斯運動二台  「2026美國網球公開賽女單十六強KALvsNAV」
             → desc 完全相同
韓國阿里郎    「Gugak The Music Of Korea」→ desc 完全相同
```

分布：阿里郎 290、博斯无限Ⅱ 77、DAZN1 67、纬来体育 63、博斯运动Ⅰ 57、博斯无限Ⅰ 53……

**为什么 `isRealDesc()` 拦不住**：它只判「≥12 字 + 非占位」。这些 desc 长度 10~41 字，
既不短也不是「暂无节目描述」，全部通过。

**★ 真正的危害不是数字虚高，是锁死补简介的位置。**
三个补简介源的循环都是同一个写法：

```js
if (isRealDesc(r.desc)) continue   // 已有简介，不动
```

复读 desc 骗过这道判断 → 这个位置被判成「已有简介」→ **真简介永远补不进来**。
实测 799 条里有 261 条本来是能被 z51 / tvmao / kbro 补上的
（DAZN1 有 46 条、纬来体育 48 条，kbro 都有对应的真简介）。

**判据（`utils.isEchoDesc`，两档）：**

| 档 | 条件 | 例 |
|---|---|---|
| ① 完全相等 | 归一化后 `desc === title` | 「Gugak The Music Of Korea」 |
| ② 标题 + 纯序号 | `desc = title + 尾巴`，剥掉数字与 `EP/季/集` 后剩余 ≤2 字 | 「麻將大師 第八季 EP17」「十八好時光 10月29日」 |

归一化 = 去空白 + 去括号内容 + 去标点 + 小写。要求标题归一化后 ≥4 字。

**★ 为什么不做「desc 以标题开头就判复读」** —— 会误伤 1177 条真简介：

| 频道 | 标题 | desc |
|---|---|---|
| 港台电视35 | The World Today | The World Today is the core rolling news service of CGTN… |
| 甘肃卫视 | 雄关剧场 | 雄关剧场是一档播放各类精彩影剧作品的节目。 |
| NOW新闻 | 世味天下 | 「世味天下」每日從全球報章中揀選特別的時事報道… |
| 中視新聞 | 即時新聞現場 | 即時新聞現場..提供全面及時的新聞資訊 |

这类「栏目名 + 栏目介绍」是完全正常的写法，一条都不能碰。

**处理：** 新增 `hasRealDesc(desc, title) = isRealDesc && !isEchoDesc`，
三处统计（`index.mjs` / `output.mjs` / `report.json`）和四处补简介判断统一改用它。
产物侧再兜一道 —— `buildXmltv` 里 desc 是复读的**直接不输出**（宁空不挂错）：
用户点开看到和标题一样的文字，比看到「暂无简介」更糟。

**结果：** 640 条被正确排除在统计外，其中 261 条被后续源补上真简介，
产物里复读 **0 条**。

### 10.2 ★ 405 条 desc 双重转义，用户看到 &quot;融媒体&quot; / &lt;甘肃新闻&gt;

源里存的是 `&amp;quot;融媒体&amp;quot;`（上游自己又把 `&quot;` 转义了一遍）。
旧 `decodeEntities` 的替换顺序是 `&quot;` 在前、`&amp;` 在最后：

```js
.replace(/&quot;/g, '"')   // 这一步跑的时候，字符串里是 &amp;quot;，不匹配
...
.replace(/&amp;/g, '&')    // 这里才变成 &quot;，但已经跑完了
```

于是产物里留着字面的 `&quot;融媒体&quot;`、`&lt;甘肃新闻&gt;`、`&amp;apos;`。

**修复：** 循环解码到稳定（最多 3 轮，防死循环）。三处重复实现
（`epgpw.mjs` / `z51.mjs` / `aggregator.mjs`）合并到 `utils.decodeEntities`。

**结果：** 405 → **0**。修完后文本正常可读：

```
[CCTV1.cn] 《生活圈》是全新的"融媒体"新闻资讯节目…
[GansuSatelliteTV.cn] <甘肃新闻>栏目通过报道宣传党的路线、方针、政策…
[GameChannel.cn] <休闲街区>栏目主要播出一些非主流的电子竞技游戏,比如:<真三国无双>…
```

### 10.3 本轮验证方法（下次照这个来）

**不能只看「字段非空」，也不能只看「长度 ≥12 字」。** 这一轮就是靠抽查具体文本才发现的：

```bash
# ① 抽 12 条真简介看内容（不是看有没有）
node .probe/verify-echo.mjs

# ② 判「desc 复读标题」有多少
node .probe/audit-i.mjs

# ③ 判「双重转义」有多少（必须先解码一次再判，否则全是假阳性）
node .probe/audit-k3.mjs

# ④ 判「跨地区串台」：同一句 desc 出现在不同地区的频道
node .probe/audit-b.mjs
```

> ⚠️ 审计脚本本身也会骗人，这一轮踩了两次：
> - **「繁体简介」判据不能当串台证据** —— 香港/台湾频道本来就用繁体，5241 条里绝大多数是对的。
> - **「含 &lt; 就是转义错误」是假阳性** —— 原始 XML 里 `&lt;` 是正确转义（内容就是 `<`），
>   必须先 `unescape` 一次再看还剩什么。
